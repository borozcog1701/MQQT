    Caso de estudio inicial

    El invernadero que preguntaba demasiado

    Un equipo instaló 20 sensores (temperatura y humedad) en tres invernaderos. La app móvil le pregunta a cada sensor por HTTP cada 5 segundos: “¿cuánto marcas?”.

    Lo que pasa

    20 sensores × 12 consultas por minuto = 240 peticiones por minuto, aunque la temperatura no haya cambiado.

    Lo que duele

    Las baterías se agotan, el Wi-Fi se satura y si un sensor se apaga, nadie se entera hasta que falla la consulta.

    Lo que piden

    Un dashboard, la app y un ventilador automático deben enterarse al instante cuando algo cambie.

    Pregunta para el grupo: ¿y si en lugar de que todos pregunten, los sensores avisaran solo cuando algo cambie, y alguien repartiera el aviso a quien le interese? Lo resolvemos al final de la sesión.
    Fundamentos

    ¿Qué es MQTT?

    MQTT (Message Queuing Telemetry Transport) es un protocolo de mensajería ligero basado en el modelo publicar/suscribir, diseñado para dispositivos con pocos recursos y redes poco confiables o de bajo ancho de banda.

    Origen

    1999, Andy Stanford-Clark (IBM) y Arlen Nipper, para monitorear oleoductos por enlace satelital.

    Estándar

    OASIS. La versión 3.1.1 también es la norma ISO/IEC 20922. La versión 5.0 se publicó en 2019.

    Transporte

    Corre sobre TCP/IP. Puerto 1883; con TLS, 8883. También sobre WebSockets.

    Ligero

    El encabezado fijo mide desde 2 bytes. Una conexión abierta sirve para muchos mensajes.

    Ojo con el nombre: a pesar de decir “Queuing”, MQTT no es una cola de mensajes clásica. Es un sistema de distribución por tópicos: un mensaje puede llegar a muchos suscriptores o a ninguno.

    ¿Dónde lo encuentras?

    • Domótica: Home Assistant, focos y enchufes inteligentes.
    • Industria 4.0: telemetría de máquinas y sensores de planta.
    • Plataformas en la nube: AWS IoT Core, Azure IoT Hub, HiveMQ Cloud.
    • Agricultura de precisión, medidores inteligentes, flotillas vehiculares.
    El modelo

    Petición/respuesta vs. publicar/suscribir

    HTTP: petición / respuesta

    • El cliente debe conocer la dirección del servidor.
    • Uno a uno y sincrónico: pregunta y espera.
    • Para enterarse de cambios hay que preguntar una y otra vez (polling).

    MQTT: publicar / suscribir

    • Publicador y suscriptor no se conocen: solo conocen al broker y el tópico.
    • Uno a muchos y asíncrono: nadie espera a nadie.
    • El dato llega cuando cambia, sin preguntar.

    Tres desacoplamientos que lo hacen poderoso

    Espacio

    No necesitas la IP del otro dispositivo.

    Tiempo

    Con sesiones persistentes, el broker guarda mensajes para quien estaba desconectado.

    Sincronización

    Publicar no bloquea al publicador mientras se entrega.

    Analogía

    El broker es una oficina de correos con apartados temáticos

    Imagina una oficina de correos donde nadie escribe la dirección de una persona. Las cartas se depositan en un apartado temático (“invernadero 1 / temperatura”) y la oficina hace copias para cada persona que pidió recibir ese tema.

    Quien envía la carta

    = cliente publicador

    La oficina de correos

    = broker

    Quien se dio de alta en un apartado

    = cliente suscriptor

    El nombre del apartado

    = tópico

    El contenido de la carta

    = payload (texto, JSON, bytes)

    El acuse de recibo

    = QoS 1 y 2

    Un mismo dispositivo puede ser publicador y suscriptor al mismo tiempo: el ventilador escucha órdenes y también publica su estado.
    El protagonista

    ¿Qué hace exactamente el broker?

    El broker es un servidor que acepta conexiones de clientes, recibe todo lo que se publica y decide a quién entregárselo.

    1. Autentica

    Verifica usuario/contraseña o certificado del cliente en el CONNECT.

    2. Recibe

    Acepta cada PUBLISH y responde según el nivel de QoS.

    3. Filtra

    Compara el tópico con los filtros de cada suscripción (incluidos comodines).

    4. Entrega

    Envía una copia a cada suscriptor que coincide.

    5. Recuerda

    Guarda mensajes retenidos y el estado de sesiones persistentes.

    6. Vigila

    Detecta clientes caídos (keep alive) y publica su Last Will.

    Tópicos

    Los tópicos: direcciones en forma de árbol

    Un tópico es una cadena UTF-8 dividida en niveles con la diagonal /. No hay que crearlo antes: existe en cuanto alguien publica en él.

    uaemexorganización/ invernadero1sitio/ zonaAárea/ temperaturamedición

    Reglas

    • Distingue mayúsculas: Casa/luz ≠ casa/luz.
    • Los espacios cuentan como caracteres: evítalos.
    • No empieces con /: crea un primer nivel vacío.
    • Los tópicos que empiezan con $ (como $SYS/…) son del broker: estadísticas internas.
    • Los comodines + y # solo van en filtros de suscripción, nunca al publicar.

    Buenas prácticas de diseño

    • De lo general a lo particular.
    • Incluye un identificador único del dispositivo.
    • Separa datos de órdenes: …/estado vs …/cmd.
    • Nombres cortos, en minúsculas y sin acentos.
    • Documenta el árbol: es el “contrato” entre equipos.
    Filtros de suscripción

    Comodines: + un nivel, # todos los demás

    + un solo nivel

    Sustituye exactamente un nivel.

    invernadero1/+/temperatura
    ✓ invernadero1/zonaA/temperatura
    ✓ invernadero1/zonaB/temperatura
    ✗ invernadero1/zonaA/suelo/temperatura
    ✗ invernadero1/temperatura

    # varios niveles

    Sustituye cero o más niveles. Debe ir al final y solo.

    invernadero1/#
    ✓ invernadero1
    ✓ invernadero1/zonaA/temperatura
    ✓ invernadero1/riego/valvula/estado
    ✗ invernadero2/zonaA/temperatura

    Probador de filtros

    Escribe un filtro y observa qué tópicos lo cumplen. Prueba #, +/+/temperatura o invernadero1/zona+.

    Entrega de mensajes

    QoS: ¿qué tanto te importa que llegue?

    QoS 0

    A lo más una vez

    “Dispara y olvida”. Sin confirmación. Si se pierde, se perdió.

    Úsalo: lecturas frecuentes donde la siguiente reemplaza a la anterior (temperatura cada 2 s).

    QoS 1

    Al menos una vez

    El receptor confirma con PUBACK. Si no llega la confirmación, se reenvía: pueden llegar duplicados.

    Úsalo: alarmas, órdenes que no importa repetir (encender = encender).

    QoS 2

    Exactamente una vez

    Intercambio de cuatro pasos. Sin pérdidas ni duplicados, pero más lento.

    Úsalo: cobros, conteos, dosificación de riego o medicamentos.

    Importante: la QoS se negocia en cada tramo. Del publicador al broker usa la QoS del PUBLISH; del broker al suscriptor usa la menor entre la del mensaje y la de la suscripción.

    Funciones del broker

    Mensajes retenidos, sesiones, keep alive y Last Will

    Retained

    Mensaje retenido

    Si publicas con la bandera retain, el broker guarda el último mensaje de ese tópico y se lo entrega de inmediato a cualquiera que se suscriba después.

    Sin esto, una app que abre a las 10:03 no sabe la temperatura hasta la siguiente lectura. Para borrarlo, publica un payload vacío con retain.

    Sesión

    Sesión limpia o persistente

    Con clean session = true (Clean Start en v5) el broker olvida todo al desconectarte. Con sesión persistente recuerda tus suscripciones y guarda los mensajes QoS 1 y 2 que te perdiste.

    La sesión se identifica por el Client ID: debe ser único.

    Keep alive

    Latido

    El cliente indica cada cuántos segundos dará señales de vida. Si no tiene nada que publicar, envía PINGREQ y el broker responde PINGRESP.

    Si pasa 1.5 veces ese tiempo sin noticias, el broker da al cliente por desconectado.

    LWT

    Last Will and Testament

    Al conectarse, el cliente le deja al broker un “testamento”: tópico + mensaje. Si se desconecta sin enviar DISCONNECT (batería, corte de red), el broker lo publica por él.

    Patrón clásico: will …/estado = "offline" retenido, y al conectarse publicar "online" retenido.

    Por dentro

    Los paquetes de control de MQTT

    Tipo Paquete Dirección Para qué sirve
    1 CONNECT Cliente → Broker Abre sesión: Client ID, keep alive, credenciales, will
    2 CONNACK Broker → Cliente Acepta o rechaza la conexión (código de retorno)
    3 PUBLISH Ambas Lleva tópico y payload
    4–7 PUBACK · PUBREC · PUBREL · PUBCOMP Ambas Confirmaciones de QoS 1 y 2
    8–9 SUBSCRIBE · SUBACK C → B · B → C Pide filtros y QoS máxima; el broker confirma la QoS concedida
    10–11 UNSUBSCRIBE · UNSUBACK C → B · B → C Cancela suscripciones
    12–13 PINGREQ · PINGRESP C → B · B → C Latido de keep alive
    14 DISCONNECT C → B Cierre ordenado (el will se descarta)

    Arma el primer byte de un PUBLISH

    Los 4 bits altos indican el tipo de paquete (3 = PUBLISH) y los 4 bajos son banderas. Cambia las banderas y observa el byte.

    Seguridad

    Un broker abierto es una puerta abierta

    Manos a la obra · 1

    Mosquitto desde la terminal

    Instala el cliente (sudo apt install mosquitto-clients en Linux, o el instalador oficial en Windows) y abre dos terminales.

    Terminal A · suscriptor

    mosquitto_sub -h test.mosquitto.org \
  -t "uaemex/ico/+/temperatura" -v

    -v muestra el tópico junto al mensaje.

    Terminal B · publicador

    mosquitto_pub -h test.mosquitto.org \
  -t "uaemex/ico/equipo3/temperatura" \
  -m "24.6" -q 1 -r

    -q 1 QoS 1, -r retenido.

    Experimento: cierra la terminal A, publica desde B con -r y vuelve a abrir A. ¿Qué recibes al instante y por qué? Luego pon -t "uaemex/ico/#" para ver lo que publican todos los equipos.
    Ver todo lo que pasa en el broker 
    mosquitto_sub -h test.mosquitto.org -t '$SYS/broker/clients/connected' -v

    Manos a la obra · 2

    Python (paho-mqtt 2.x) y ESP32 (PubSubClient)

    Python · dashboard suscriptor

    # pip install paho-mqtt
import paho.mqtt.client as mqtt

def on_connect(client, userdata, flags, reason_code, properties):
    print("Conectado:", reason_code)
    client.subscribe("uaemex/ico/+/temperatura", qos=1)

def on_message(client, userdata, msg):
    print(msg.topic, "→", msg.payload.decode())

cliente = mqtt.Client(mqtt.CallbackAPIVersion.VERSION2,
                      client_id="dashboard-equipo3")
cliente.on_connect = on_connect
cliente.on_message = on_message
cliente.connect("test.mosquitto.org", 1883, keepalive=60)
cliente.loop_forever()

    Suscribirse dentro de on_connect hace que, si se cae la red y se reconecta, la suscripción se renueve sola.

    ESP32 · sensor publicador con LWT

    #include <WiFi.h>
#include <PubSubClient.h>

WiFiClient red;
PubSubClient mqtt(red);
const char* EST = "uaemex/ico/equipo3/estado";

void conectar() {
  while (!mqtt.connected()) {
    // id, tópico will, QoS will, retain will, mensaje will
    if (mqtt.connect("esp32-equipo3", EST, 1, true, "offline")) {
      mqtt.publish(EST, "online", true);
    } else delay(2000);
  }
}

void setup() {
  WiFi.begin("MI_RED", "MI_CLAVE");
  while (WiFi.status() != WL_CONNECTED) delay(500);
  mqtt.setServer("test.mosquitto.org", 1883);
}

void loop() {
  if (!mqtt.connected()) conectar();
  mqtt.loop();   // mantiene el keep alive
  static unsigned long t = 0;
  if (millis() - t > 5000) {
    t = millis();
    String v = String(analogRead(34) * 0.08, 1);
    mqtt.publish("uaemex/ico/equipo3/temperatura", v.c_str());
  }
}

    La conversión * 0.08 es solo de ejemplo: usa la fórmula de tu sensor. PubSubClient publica con QoS 0.

    Errores comunes

    Error Qué pasa Cómo evitarlo
    Dos dispositivos con el mismo Client ID El broker desconecta al primero cuando entra el segundo; se “patean” en bucle ID único: incluye la MAC o un número de serie

    Caso resuelto

    Antes · HTTP polling

    • 240 peticiones por minuto aunque nada cambie.
    • Cada petición abre conexión y repite encabezados HTTP de cientos de bytes.
    • Un sensor caído se descubre por un error.
    • La app debe conocer la IP de los 20 sensores.

    Después · MQTT

    • Cada sensor mantiene una conexión y publica solo cuando cambia (o cada cierto tiempo).
    • Encabezado desde 2 bytes.
    • Dashboard, app y ventilador se suscriben con filtros como uaemex/+/+/temperatura.
    • Valores retenidos: la app muestra el dato al abrirse.
    • LWT avisa “offline” en cuanto un sensor se cae.
